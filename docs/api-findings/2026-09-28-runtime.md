## Nomes de campo confirmados por leitura do PRD/dataS (não testados em jogo)

- `spec_motorized.motor` (`VehicleMotor`): `minRpm`, `maxRpm`,
  `peakMotorTorque`, `peakMotorPower` (kW), `maxForwardSpeed`,
  `torqueCurve.keyframes` (cada keyframe é `{torque, time=rpm}`, conforme
  comentário do PRD em `Motorized.lua:1338`), `minForwardGearRatio`/
  `maxForwardGearRatio` (só existem em motor CVT), `forwardGears`/
  `gearGroups` (arrays de tabelas com campo `.ratio`).
- `spec_motorized.differentials[i]`: `torqueRatio`, `maxSpeedRatio`,
  `diffIndex1`, `diffIndex1IsWheel`, `diffIndex2`, `diffIndex2IsWheel`
  (`Motorized.lua:1191-1198`, citado no PRD). O índice do diferencial ativo é
  escolhido pela configuração de rodas (`wheels#differentialIndex`), então os
  diferenciais expostos em `spec_motorized.differentials` já são os da
  configuração selecionada — o reader não precisa (e não deve) escolher entre
  configurações de diferencial.
- `vehicle:getWheels()[i]`: `.physics.radius`, `.physics.width`,
  `.physics.wheelShapeWidth`, `.physics.restLoad`, `.physics.frictionScale`,
  `.physics.tireType`, `.isLeft`, `:getMass()` (soma `physics.mass +
  additionalMass`, PRD "Rodas").
- `WheelsUtil.getTireTypeName(tireType)` e
  `WheelsUtil.getTireFriction(tireType, WheelsUtil.GROUND_FIELD, 0, 0)`
  (assinatura `(tireType, groundType, wet, snow)`, PRD "Rodas"; usamos
  `wet=0, snow=0` para o atrito de campo seco, conforme convenção F6 do spec
  de "não fazer" atrito em estrada/molhado/neve).
- `vehicle:updateMass()` + `vehicle:getTotalMass(true)`: é exatamente o que
  `Vehicle.getSpecValueWeight` já chama para a linha "peso" vanilla da loja
  (PRD "Massa"), então ler assim reproduz o mesmo número que o jogo mostra.
- `g_brandManager:getBrandByIndex(storeItem.brandIndex)`: o PRD não confirma
  se o campo de nome é `.title` ou `.name`; o reader tenta `.title` primeiro e
  cai para `.name` (`brand.title or brand.name`). **Não verificado em jogo.**

## Incertezas explícitas ("[A VALIDAR]" no código)

- **`additionalCount(w)`** (`RuntimeVehicleReader.lua`): o spec da Fase 3 diz
  para contar `#w.visualWheels - 1`, com fallback 0, marcando
  "[A VALIDAR na Fase 3]". Implementei exatamente essa fórmula, assumindo que
  `visualWheels` inclui a própria roda física como primeiro elemento (então
  `-1` sobra só as rodas duplas/triplas adicionais). Não há como confirmar
  isso sem abrir o jogo com um veículo de rodas duplas (ex.: Ford 8030 com
  `DUPLA TRAZERA`, um dos casos da tabela de coleta in-game). Se o campo não
  existir ou tiver outro significado, o `guard` em torno do bloco `wheels`
  evita que isso quebre a leitura — o pior caso é `additionalCount` sempre 0.
- **`PreviewSource.list()` e bundles**: o PRD nota que
  `processAttributeData` roda uma vez por item de bundle
  (`storeItems`), com `vehicle` possivelmente único mas
  `previewVehicles[i]` múltiplo. Não há confirmação de que
  `g_shopConfigScreen` exponha um array paralelo `storeItems` (plural) —
  supus esse nome por analogia com o parâmetro `storeItems` do hook
  `registerCustomSpecValues`. Se não existir, o código cai de volta para
  `screen.storeItem` (singular) para todos os previews, o que é
  provavelmente errado só no caso raro de bundle com storeItems diferentes.
  **A validar assim que houver um veículo em bundle disponível para testar.**
- **Valtra BH180 (fallback de motor parcial)**: o PRD documenta que várias
  configurações do Valtra só têm `torqueScale` e herdam o resto de
  `motorConfiguration(0)`, e que o hp calculado da BH180 (~162 cv) diverge do
  hp declarado (180). O reader lê `spec_motorized.motor` como o jogo já o
  resolveu (o fallback é feito pelo motor do jogo antes do preview existir),
  então essa divergência deve aparecer naturalmente como
  `declared.powerHp ≠` métrica calculada de potência — é exatamente o
  comportamento esperado (requisito de distinguir declarado × calculado). Não
  testado em jogo.
- **Se a massa em loja inclui combustível**: não verificado neste ambiente.
  `vehicle:getTotalMass(true)` é chamado com `onlyGivenVehicle=true`, igual ao
  vanilla `Vehicle.getSpecValueWeight`, então deveria refletir o que a loja já
  mostra — mas isso só pode ser confirmado comparando o valor do dump com o
  peso exibido na tela de configuração in-game.
- **Se `peakMotorPower` bate com F2 recalculado da curva**: é exatamente o
  item (d) do `golden_spec.lua`, que fica `pending` até existirem dumps reais.

## Decisões de projeto tomadas nesta fase (sem ambiguidade do spec, registradas por transparência)

- `RuntimeVehicleReader.read` consulta `NS.app.settings` diretamente (em vez
  de receber `settings` como parâmetro) para checar
  `debug#enabled`/`debug#simulateFailure=="reader"`, porque a assinatura
  pedida no spec é `read(vehicle, storeItem, logger)` — sem um parâmetro de
  settings. Isso é consistente com o padrão de outros adapters do projeto
  (ex.: `SafeCall` acessa `NS.app.logger`/`NS.app.state` como módulos
  compartilhados, não por injeção de parâmetro).
- `SnapshotXmlWriter.write` roda tudo dentro de um `pcall` interno e devolve
  `nil` (com log DEBUG) em vez de propagar erro, para que uma falha ao gravar
  um veículo não interrompa `vpDump` para os demais itens do preview.
- `Console.vpAnalyze`/`vpDump` também envolvem cada item do preview em
  `pcall` individual, pela mesma razão.
